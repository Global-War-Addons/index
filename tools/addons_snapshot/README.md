# addons_snapshot — снимок базы GlobalWar для каталога аддонов

> Пути в командах ниже — как в репозитории каталога `index` (`tools\addons_snapshot`, туда папку копирует
> `catalog/assemble.py`). В воркспейсе GW папка лежит в `GlobalWar\utils\addons_snapshot`.

Генератор «снимка базы» из `plans/addons_api_support/12-addon-breakage-without-api.md` §4.2 (решение 2026-11-04:
вариант V3 — только снимок; аддоны каталога перепроверяются только на релизах игры; жёлтая метка — только
предупреждение).

Снимок — это список того, на что может сослаться аддон: файлы, секции ltx, строки, id текстур UI, пути UI xml,
функции Lua-модулей, события. Плюс нормализованные тексты всех `.script`/`.ltx`/`.xml` — предок, от которого CI
каталога считает дельту аддона, заменившего файл базы, и сливает её с новой базой (`13-extension-model.md` §4.6).
Кто снимок потребляет — CI каталога (`11-catalog-distribution.md` §4: `build-index.yml`, валидатор §4.7). Лаунчер
снимок не качает.

Подкоманды:

| Команда | Что делает |
|---|---|
| `build` | папка gamedata релиза → `base_snapshot.json.gz` + `base_texts.tar.gz` |
| `diff` | снимок A против снимка B → markdown «Изменения для аддонов» (раздел патч-нотов, чек-лист перед релизом) |
| `check` | папка аддона против снимка → список битых ссылок (заготовка этапа S2, простые случаи) |
| `delta` | дельта S9 аддона против текстов снимка версии автора → `<аддон>\.gw_merge\delta.json`, `--out` или каталог `--catalog` (раздел «Дельты S9») |
| `rebase` | перенос дельты (файл дельты или `files/<id>/<ver>.json` каталога) на новый снимок → `checked[].rebase` индекса (шаг 5 CI) |
| `pairs` | пересечения атомов аддонов и общие скрипты (компиляция слияния) → `merge_conflicts.json`, `merge_stats.json` (шаг 6 CI) |

Нужен только Python 3.8+ из коробки: сторонних зависимостей нет (`json`, `gzip`, `tarfile`, `hashlib`, `re`).
`delta`, `rebase`, `pairs` и атомы в `check` зовут утилиту `gw_merge` (C++, та же библиотека слияния, что в движке).

## Быстрый старт

```bat
rem 1. Снимок релиза. --tag — тег релиза игры, он попадает в снимок и в заголовок диффа
rem    (схема тегов — раздел «Теги релизов игры»).
rem    --out — папка для результата (создаётся). В репозиторий результат не класть.
python tools\addons_snapshot\gw_snapshot.py build GlobalWar\gamedata --tag v1.4.0 --out out\v1.4.0

rem 2. Что пропало между двумя релизами: готовый раздел «Изменения для аддонов».
python tools\addons_snapshot\gw_snapshot.py diff out\v1.3.0\base_snapshot.json.gz out\v1.4.0\base_snapshot.json.gz --out changes.md

rem 3. Битые ссылки аддона. --old-snapshot — снимок версии игры, под которую аддон делали:
rem    с ним check отличает «модуль удалён» от «неизвестного глобального имени».
python tools\addons_snapshot\gw_snapshot.py check out\v1.4.0\base_snapshot.json.gz path\to\my_addon --old-snapshot out\v1.3.0\base_snapshot.json.gz
```

`check` возвращает код 1, если нашёл битые ссылки, и 0, если нет — CI может писать по нему `broken` в индекс.

## Теги релизов игры

Тег релиза игры (`build --tag`, `configs\gw_release.ltx`, `[addon] game_version`, `game_releases.ltx` каталога)
разбирается и сравнивается как в движке (`MergeParseTag`); код — `gametag.py`, один на инструменты и валидатор
каталога:

- необязательная `v`/`V` в начале, затем числа через точку (ASCII-цифры, не больше 4294967295, ведущие нули
  допустимы: `04` = `4`); недостающие части при сравнении — 0 (`v1.4` = `1.4.0`); пробелы вокруг — не тег;
- необязательный суффикс `-patchN` (`patch` в любом регистре, `N` — цифры) — номер патча релиза;
- любой другой суффикс `-<ASCII-буквы, цифры, точки>` — пре-релиз (в том числе `-patch`, `-patch4b`, `-patch4.1`);
- при равных числах: пре-релиз < релиз < `-patch1` < `-patch2` …; два пре-релиза — строки без учёта регистра.

Пример порядка: `0.5.5-Beta` < `0.5.5` < `0.5.5-patch1` < `0.5.5-patch4` < `0.5.6-Beta` < `v0.5.6`. Тег вне
схемы движок сравнивает только на равенство (любое отличие `game_version` — «старее»): `build` и
`write_gw_release.py` о таком теге предупреждают. `delta` сравнивает `game_version` с тегом снимка этой же схемой
(`v1.4` и `1.4.0` — одна версия). Версии и теги релизов самих аддонов каталога (`v<MAJOR.MINOR.PATCH>`) — другая
схема, она не менялась.

## build

```
gw_snapshot.py build <gamedata> --tag <тег> --out <папка>
    [--texts tar|inline|none]      где хранить тексты (по умолчанию tar, см. «Почему тексты отдельно»)
    [--exclude GLOB ...]           ещё исключения по виртуальному пути (fnmatch по всему пути, '*' проходит через
                                   папки: '*.bak' — все .bak на любой глубине)
    [--no-default-excludes]        не исключать *.pl, helpers\, tools\
    [--no-hash]                    без sha256 (быстрый локальный прогон; в files будет null вместо хеша)
    [--hash-cache FILE]            кэш хешей {путь: [размер, mtime_ns, sha256]} для повторных прогонов
    [--workers N]                  потоки для sha256 (по умолчанию min(16, число ядер))
    [--events-meta FILE]           events_meta.json (иначе ищется, см. «События»)
    [--engine-src DIR]             xray-16/src/xrGame: встроенные события движка и их схемы
    [--no-auto]                    не искать ../../xray-16 рядом с gamedata
    [--console-dump LOG]           лог с выводом консольной команды help (cvar)
    [--bindings-dump FILE]         ScriptBindings_N.txt от движка с ключом -dump_bindings
```

Вход — **распакованный** gamedata (как в релизе). Архивы `.db` не читаются: пайплайн релиза запускает генератор по
папке, из которой эти архивы собирает.

Исключается всегда: всё, что начинается с точки (`.git`, `.vscode`, `.gitattributes`…), и `__pycache__`.
По умолчанию ещё: `*.pl` (на любой глубине; сейчас они лежат в корне и в `helpers\`), `helpers\`, `tools\` —
служебные скрипты репозитория, в релиз не идут. Папки и файлы обходятся по алфавиту, поэтому из путей, которые
отличаются только регистром (возможно на Linux), в `files` всегда попадает один и тот же.

Предупреждения и замеры печатаются в stderr.

## Результат

```
<out>/
  base_snapshot.json.gz   снимок (json, gzip); ключи отсортированы, gzip без времени
  base_texts.tar.gz       нормализованные тексты (только при --texts tar)
```

`base_texts.tar.gz` детерминирован (порядок по пути, mtime 0, gzip без времени): у одинакового gamedata
одинаковый sha256 (при той же версии zlib в Python). В `base_snapshot.json.gz` от прогона к прогону меняется только
`game.created`; если задана переменная окружения `SOURCE_DATE_EPOCH` (секунды Unix), время берётся из неё, и
повторная сборка того же gamedata даёт побайтно тот же файл.

### Схема (`schema_version` 1)

Виртуальный путь (`vpath`) везде — путь относительно gamedata, **в нижнем регистре, с обратными слешами**, как его
видит ФС движка на Windows: `configs\system.ltx`, `scripts\sim_smart.script`.

без подъёма версии; удаление или смена смысла ключа — подъём `schema_version`.

### Почему тексты отдельно

Замер на `GlobalWar\gamedata` 2026-11-04 (84 703 файла, 31,1 ГБ; 4 790 текстовых, 49,7 МБ после нормализации):

| Вариант | Размер | Загрузка json (`json.load` из gz) |
|---|---|---|
| `--texts tar` (по умолчанию) | json.gz 5,2 МБ (32,4 МБ json) + tar.gz 4,8 МБ | 0,28 с; tar целиком — 0,12 с |
| `--texts inline` | json.gz 9,9 МБ (84,2 МБ json) | 0,56 с |

По сжатому размеру разницы нет, поэтому выбран отдельный `tar.gz`: `diff` и `check` тексты не нужны (в памяти
32 МБ вместо 84 МБ), а CI каталога, которому нужен предок, распаковывает tar в папку и сразу кормит файлы
`git merge-file` / diff3. Целостность пары — `texts.storage.sha256` и `texts.files[*].sha256`.

## Как разбирается

### Нормализация текстов (`textnorm.py`)

Декодирование: UTF-8 (строго); не получилось — Windows-1251, как делает сам движок; байт, которого нет и в cp1251
(`0x98`), заменяется на U+FFFD с пометкой `cp1251-lossy`. BOM в начале снимается. CRLF → LF (одиночный CR
остаётся в тексте; разборщик ltx, как и движок, считает его концом строки). Исходные кодировка, BOM и переносы записаны в `texts.files`, чтобы слитый файл можно было вернуть в той
же кодировке (правило «не менять кодировку существующего файла»).

### ltx (`ltxparse.py`)

Повторяет `CInifile::Load` (`xray-16/src/xrCore/Xr_ini.cpp`) в режиме «только чтение», как грузятся `pSettings`
и `pGameIni`:

- деревья движка — те, что грузит `InitSettings` (`xray-16/src/xrEngine/x_ray.cpp`): `system.ltx`, `game.ltx`,
  `openxray.ltx`, `faction_editor_config.ltx`. `game.ltx` — отдельный корень (не подключается из `system.ltx`);
- строки — как их читает `IReader::r_string`: конец строки — CR или LF (одиночный CR тоже разрывает строку); с краёв
  срезаются все символы `<= ' '`, включая управляющие;
- комментарии: `;` где угодно; `//` — только если это **первый** `/` в строке и он стоит до `;`; символ
  комментария внутри первой пары кавычек строку не режет;
- `#include "имя"` — путь от папки подключающего файла, расширение любое (`#include "x.inc"` тоже грузится, такой
  файл попадает и в `texts`). Маска `*.ltx` перебирает папку маски **рекурсивно** и сравнивает путь относительно
  неё со всем именем (`PatternMatch`, `*` проходит и через `\`; с учётом регистра, а имена в ФС движка в нижнем
  регистре, поэтому `Weapons_*.ltx` ничего не находит; несколько масок через `,`), по алфавиту; файлы,
  найденные по маске, получают базой папку маски — как в движке (поэтому маска с подпапкой, `sub\*.ltx`, ничего
  не находит). Сейчас масок в базе нет;
- `[имя]:родитель1, родитель2` — имя в нижнем регистре; список делится как в `_GetItemCount`/`_GetItem` (`[a]:` и
  запятая в конце лишнего родителя не дают, `,,` обрывает список пустым родителем); родитель должен быть уже
  загружен (иначе движок падает `Can't find section`). Секция сохраняется, когда начинается следующая или кончается файл, — поэтому секция,
  открытая в подключающем файле, ещё не видна подключаемому;
- `ключ = значение` / `ключ`: регистр имени ключа сохраняется; значение с нечётным числом кавычек продолжается на
  следующих строках, пока кавычки не закроются; строка с `[…]` или конец файла прерывает его, и разбор идёт дальше
  со строки после ключа (как в движке); предел буфера значения в 4096 байт не воспроизводится;
- строки до первой секции пропускаются; **значения ключей не хранятся** (они есть в текстах).

Где движок упал бы (повтор секции, нет родителя, нет файла `#include`), снимок пишет запись в `errors` и идёт дальше.

ltx в `configs\`, которые не попали в деревья движка, разбираются как отдельные деревья (`standalone_roots`): корень —
файл, который не подключает ни один другой такой файл. Ошибки `missing_parent` в них — норма для фрагментов,
рассчитанных на контекст `system.ltx` (например `creatures\spawn_sections_*.ltx`, которые `system.ltx` сейчас не
подключает).

DLTX (`![секция]`, `!![секция]`, `@[секция]`, `![s]:!родитель,новый`) движок пока не поддерживает (план
`09-content-addons-vfs.md` §5.1), поэтому в базе он не разбирается; разборщик заголовков для `check` его понимает.

### Строки, текстуры, UI xml (`xmlscan.py`)

xml движка — не строгий XML (бывает без общего корня, с `#include`, с неверным объявлением кодировки), поэтому
структура читается терпимым сканером тегов (комментарии, CDATA, `<? ?>` пропускаются; незакрытые теги
закрываются концом родителя). Регистр тегов сохраняется.

- строки — `<string id="…">`, прямые дети корня (первого элемента верхнего уровня, как `GetRoot()` движка), из
  `configs\text\<язык>\**\*.xml` (маска движка `text\<язык>\*.xml`); при повторе id побеждает поздний по пути файл;
- текстуры — `<texture id="…">`, прямые дети `<file name="…">` под корнем, из `configs\ui\textures_descr\**\*.xml`;
  при повторе id побеждает поздний по пути файл;
- пути UI — все уникальные пути узлов `configs\ui\**\*.xml`, кроме `textures_descr`.

### Lua (`luascan.py`)

Лёгкий лексический разбор, не парсер: токенизатор понимает комментарии `--`, `--[==[ ]==]`, строки `"…"`, `'…'`,
`[==[ ]==]`. Глубина блоков считается по ключевым словам (`function`, `do`, `if`, `repeat` открывают; `end`,
`until` закрывают), вложенность — по `()`, `{}`, `[]`. «Верхний уровень» — вне блоков и скобок.

Собирается: `function a(…)`, `function a.b(…)`, `function a:b(…)`, `a = function(…)`, `a.b = function(…)` с числом
объявленных параметров и `...` (при повторном определении — последнее: оно действует после загрузки файла);
`a = {…}` (таблицы), прочие `a = …` (переменные), `class "x"`, глобалы,
присвоенные внутри функций, и поля `m.x = …`.

Ограничения:

- областей видимости нет: локальные имена собираются на весь файл (`local`, параметры, переменные `for`), поэтому
  `check` может пропустить обращение, если где-то в файле есть локальная переменная с тем же именем;
- `a, b = 1, 2` не записывается; присваивание внутри функции, которая сама стоит в конструкторе таблицы
  (`{ f = function() x = 1 end }`), не видно;
- `setfenv`, `rawset`, `_G[...]`, имена, собранные во время выполнения, не видны;
- у методов `a:b` в `params` — объявленные параметры, без неявного `self`;
- файлы в подпапках `scripts\` (`gw_faction_editor\*.script`) — не глобальные модули, а `require` (`kind: require`).

### События

- `script` — таблица `local intercepts = {…}` из `scripts\axr_main.script` (имя → схема аргументов);
- `builtin` — `kBuiltinNames`/`kBuiltinSchemas` из `addon_event_bus.cpp` (`--engine-src`, папка `xray-16/src/xrGame`);
- `meta` — `events_meta.json` целиком. В репозитории он лежит **в движке**: `xray-16/src/gw_plugins/events_meta.json`
  (в gamedata его нет). Порядок поиска: `--events-meta`; файл `events_meta.json` внутри gamedata; без `--no-auto` —
  `<gamedata>\..\..\xray-16\src\gw_plugins\events_meta.json` (раскладка папки GW). Так же ищется `--engine-src`.

В пайплайне релиза лучше передавать оба пути явно и с `--no-auto`: снимок должен описывать движок того же релиза.

## diff

```
gw_snapshot.py diff <старый снимок> <новый снимок> [--out changes.md] [--limit 200] [--format md|json]
```

Пишет markdown «Изменения для аддонов»: сводная таблица и списки — удалённые Lua-модули, функции/таблицы/переменные
модулей, смена числа параметров; удалённые секции ltx, смена родителей, потерянные ключи **с учётом наследования**,
секции, переехавшие в другой файл (замена старого файла перестаёт действовать); удалённые строки по языкам, id
текстур UI, пути UI xml; удалённые события и смена их схемы (сравниваются только источники `meta`, `builtin`,
`script`, которые есть в обоих снимках; остальные названы в сводке); cvar и строки дампа экспортов (если дампы есть
в обоих снимках); удалённые файлы. Добавленное только считается. Отдельное дерево ltx, корень которого стал
подключаться из другого файла, удалённым не считается: его секции ищутся во всех деревьях нового снимка, а
«удалённое дерево» — только если удалён сам корневой файл. `--limit` — сколько пунктов на список (0 — все).
`--format json` — те же данные для машин.

## check (заготовка S2)

```
gw_snapshot.py check <снимок> <папка аддона> [--old-snapshot <снимок версии автора>] [--format md|json] [--out FILE]
```

Папка аддона: если в ней есть `gamedata\`, контент берётся оттуда (раскладка `09-content-addons-vfs.md` §2.1),
иначе сама папка считается корнем gamedata (старые моды и фикс-паки).

Проверяется сейчас:

| Что | Правило |
|---|---|
| родители секций `[a]:b,c` в ltx аддона | `b`, `c` есть в каком-нибудь дереве снимка или объявлены самим аддоном |
| цели DLTX `![a]`, `!![a]` (и родители `![a]:x`; `!x` — снятие родителя, не проверяется) | секция есть в снимке или в аддоне |
| `#include "…"` в ltx аддона (без масок) | файл есть в снимке или в аддоне |
| `модуль.имя` в скриптах аддона, где `модуль` — глобальный модуль базы | `имя` — функция, таблица, переменная, класс, runtime-глобал модуля или его кладут в модуль (`injected`), либо его определяет сам аддон |
| то же для модулей, которые аддон приносит своими файлами | имя есть в файле аддона (его копия заменяет файл базы целиком) или его кладут в модуль другие скрипты базы |
| `модуль.имя`, где `модуль` был в `--old-snapshot` и пропал | «модуль удалён» |
| `RegisterScriptCallback("имя")` / `UnregisterScriptCallback` | событие объявлено (`meta`, `script`, `builtin`) или его использует сама база |

Отдельно (не ошибки): какие файлы базы аддон заменяет и совпадают ли они с базой (текст, который отличается только
переносами строк или BOM, считается совпадающим); неизвестные глобальные имена
`X.y` (не модуль базы, не встречаются в базе, не локальные) — это может быть удалённый модуль, если нет
`--old-snapshot`.

Атомы заменённых файлов: если найдена утилита `gw_merge` (`--gw-merge`, `$GW_MERGE`, `PATH`,
`xray-16\bin\x64\Release`) и рядом со снимком лежит `base_texts.tar.gz`, у каждого заменённого `.ltx`/`.xml`/`.script`,
который отличается от базы, выводится список атомов `gw_merge atoms` (`+` добавлен, `~` изменён, `-` удалён; в json —
`info.replaced[].atoms`). Это то, что слияние движка без дельты сочтёт правками аддона: у аддона, сделанного на старой
версии, сюда попадают и правки базы, которые он откатит. Утилиты нет — атомов нет, остальное как раньше.

Не проверяется (TODO): id строк и текстур, которые использует аддон; пути XMLOverride; значения ключей ltx,
ссылающиеся на секции, модели, текстуры, звуки; `obj_on_job`/смарты в логике; голые вызовы глобалов `_g.script`;
`get_console_cmd`/`execute` cvar; `#include` шейдеров; экспорты движка.

## Дельты S9: delta, rebase, pairs

План `plans/addons_api_support/15-merge-implementation.md` §2.3–2.4, §7; решения `00-roadmap.md` §5а п.47, 48, 50.
Аддон, который целиком заменяет текстовый файл базы, сделан на какой-то версии игры. Когда база обновится, слияние
движка с текущей базой как предком откатило бы её правки. Дельта хранит для каждого атома, который аддон изменил,
текст в базе версии автора (предок) и новый текст. Движок переносит её на текущую базу: атомы, которых в дельте нет,
берутся из базы. Тексты базы ни движок, ни лаунчер не качают — всё нужное лежит в дельте.

Всё считает `gw_merge` (цель CMake `gw_merge`, `xray-16/src/utils/gw_merge`): Python-копии алгоритма нет, чтобы
прогноз CI не расходился с игрой. Где искать утилиту: `--gw-merge`, переменная `GW_MERGE`, `PATH`,
`xray-16\bin\x64\Release` (затем `Debug` и `xray-16\bin`). Версию разбора (`algo` дельт) инструменты не зашивают:
её сообщает сам `gw_merge` (поле `algorithm` его JSON).

`delta`, `rebase` и `pairs` без `gw_merge` не работают (решение 63 п.4: утилита входит в релиз игры, запасных
Python-портов её решений больше нет). Не найдена или слишком старая (нет команды `version` или `plan` с
`--all-files`) — `error: ...` в stderr и код выхода 2; в тексте — где искали и где взять:

- из игры: `<игра>\bin\gw_merge.exe` (лежит рядом с движком);
- Linux: ассет `gw_merge-linux-x86_64.tar.gz` релиза xray-16 (его качает CI каталога —
  `catalog/index/ci/fetch_gw_merge.sh`);
- собрать: `cmake -S xray-16/src/utils/gw_merge -B build-gw_merge && cmake --build build-gw_merge --config Release`.

Путь передаётся через `--gw-merge <путь>` или `$GW_MERGE`. Поиск и проверка — одна функция
`gwmerge.require_gw_merge` (её текст ошибки возвращает и `gwplan.unavailable`, которую вызывает валидатор каталога).

Каждый вызов `gw_merge` ограничен по времени: `--gw-merge-timeout <сек>` (у `delta`, `rebase`, `pairs`, `check`),
иначе переменная `GW_MERGE_TIMEOUT`, иначе 300 с; `0` — без ограничения. Предел нужен только против зависшей утилиты
(дельта фикс-пака на 77 файлов — около 1 с). Превышение, падение `gw_merge`, битый JSON и отказ перезаписать файл —
строка `error: ...` (с файлом и командой `gw_merge`) и код выхода 2.

JSON, который инструменты читают (дельты, файлы каталога, отчёты `gw_merge`), с повтором ключа считается битым: такой
файл разные читатели поняли бы по-разному (`json.load` молча берёт последнее значение).

На Windows `gw_merge` берёт аргументы в UTF-16 (`CommandLineToArgvW`) и открывает файлы по путям в Unicode, поэтому
пути с кириллицей и другими символами вне кодовой страницы системы (в том числе в `%TEMP%`, куда распаковываются
тексты) работают.

### delta — дельта аддона

```bat
rem Автор локального аддона или CI. --snapshot - снимок тега, на котором сделан аддон ([addon] game_version),
rem рядом с ним base_texts.tar.gz. --latest - последний снимок: файлы, которых не было в базе автора, но есть в
rem текущей, получают not_in_ancestor (для них работает слияние S8). Результат по умолчанию -
rem <аддон>\.gw_merge\delta.json (так его кладёт лаунчер), --out <файл> - в другой файл, --out - - в stdout
rem (отчёт тогда идёт в stderr). Существующий файл не перезаписывается без --force.
python tools\addons_snapshot\gw_snapshot.py delta path\to\my_addon --snapshot out\v1.3.0\base_snapshot.json.gz --latest out\v1.4.0\base_snapshot.json.gz
```

`--catalog <папка index>` — дельта в раскладке каталога (решение 00 §5а п.51), id и версия — из `addon.ltx`:

- новая версия — дельта в `files/<id>/<ver>.merge.json`; `files/<id>/<ver>.json` инструмент не пишет и не меняет
  (его пишет только валидатор каталога, по схеме — ревью F19): ссылка
  `"merge": {"file": "<ver>.merge.json", "algo": "<algo>", "sha256": "<hex файла>", "size": N}` печатается в
  отчёте (`merge`) и предупреждении;
- `<ver>.json` уже ссылается на дельту другой версии разбора (`algo` у `gw_merge` новее) — пересчёт в
  `files/<id>/<ver>.merge.<algo tag>.json` (`/`, `\`, `:` → `-`, например `1.2.0.merge.gw-merge-2.json`);
  `<ver>.json` и `<ver>.merge.json` не меняются;
- файлы каталога неизменяемы: существующий `<ver>.merge.json` (или пересчёт той же версии) — ошибка без `--force`;
- в пакете нет заменённых `.ltx` / `.xml` / `.script` — в каталог ничего не пишется, ссылки нет.

`gw_merge` пишет дельту во временную папку: при ошибке старый файл остаётся.

Какие тексты идут в дельту — как их сливает движок (`addon_merge.cpp`, ревью B3, B9, B21, B22): `.ltx`, `.xml`,
`.script`, `.lua` (расширение в любом регистре ASCII) всех слоёв аддона — `gamedata\` и наборов `[slot.*] files`
(`<files>\gamedata\`, по умолчанию `slots\<слот>\`); не входят файлы под масками `[private]`, скрытые, `.*`, папки
`@...`, имена `ignore_name` и патчи `mod_<stem>_<rest>.<ext>` под `configs\`, у которых в той же папке (база или
аддон) есть `<stem>.<ext>`; `mod_*` без такой цели — обычный текст. Регистр путей понижается только для ASCII, как в
движке. Файл, который есть и в `gamedata\`, и в наборе, берётся из `gamedata\` (предупреждение: при выбранном
поставщике движок отдаёт файл набора, и дельта для него устареет); файл двух наборов в дельту не идёт
(предупреждение). Выбранные файлы складываются во временную папку `<папка>\gamedata\` и отдаются `gw_merge delta
--addon`.

Решение 63: слои аддона и их тексты (маски `[private]`, скрытые и `.*` записи по правилу ОС, папки `@...`,
`ignore_name`, патчи `mod_*`), его `patches` и то, что решает патч совместимости пары (применён, `stale`,
`not_a_side`), берутся из `gw_merge plan` (`gwplan.py`, `plan --all-files`). Python-портов этих правил больше нет
(решение 63 п.4): `gw_merge` обязателен. Папка без `addon.ltx` для движка не аддон — текстов у неё нет
(предупреждение), дельта пустая.

Распаковываются только тексты файлов аддона, затем `gw_merge delta --ancestor-dir <тексты> --addon <аддон>
--game <тег>`. В выводе — число файлов и атомов, размер, предупреждения валидатора:

- `one atom (kind lines)` — самопроверка без потерь не прошла (аддон переставил атомы, правка вне атомов): файл
  записан одним атомом `@lines`, перенос — diff3 по строкам;
- `the texts of the delta take N KB` — больше 1 МБ текстов: файл заменён почти целиком, правки лучше переписать на
  DLTX / XMLOverride / хуки;
- `N file(s) are the same as the base` — файл не изменён, его стоит убрать из пакета;
- `[addon] game_version is not set` — версия базы угадана (`guessed`).

Формат `delta.json` — §7.2 плана: `{"format": 1, "algo": "gw-merge/2", "game": "<тег>", "guessed": false, "files":
{"<vpath>": {"kind", "ancestor_sha256", "addon_sha256", "atoms": [{"atom", "op", "path", "after", "anchor",
"ancestor", "text"}]}}}` (`algo` — версия разбора `gw_merge`, которым дельта сделана). Тот же JSON без изменений —
файл `files/<id>/<ver>.merge.json` каталога.

### Шаги CI каталога (§7.2)

CI каталога (`build-index.yml`, 11 §4.2) ещё не существует. Ниже — команды, которые запускают его шаги; локально они

| — | новая версия разбора (`algo` у `gw_merge`): дельты пересчитываются по снимку тега автора в отдельный файл `files/<id>/<ver>.merge.<algo tag>.json` (`/` → `-`, например `1.2.0.merge.gw-merge-2.json`), `<ver>.json` и `<ver>.merge.json` не меняются | та же команда шагов 2–4 новым `gw_merge`: `--catalog` сам выбирает файл пересчёта |

`rebase` и `pairs --catalog` берут дельту версии так же, как лаунчер: `<ver>.merge.<algo tag>.json` для `algo` этого
`gw_merge`, если файл есть, иначе файл ссылки `merge` — со сверкой `sha256` и `size` (не сошлось — ошибка у `rebase`,
предупреждение и аддон без дельты у `pairs`). `rebase` принимает и сам файл дельты (`delta.json`, `<ver>.merge*.json`).

У игрока лаунчер кладёт дельту (пересчитанную под версию разбора движка, если она есть) всегда в
`<аддон>\.gw_merge\delta.json` — движок читает только этот файл и сверяет его `algo`; файлы `delta.<...>.json` никто
не читает (ревью 2026-11-06 §4.1 п.1). Версию разбора движок пишет в `merge_summary.algo` отчёта
`addons_report.json`.

Код выхода: `rebase` — 1, если есть конфликты переноса или файл не перенёсся (`failed`: разборщик не понял новую
базу, `bad_path`: ключ дельты не vpath); `pairs` — 1, если есть пары с конфликтом или `fallback` без работающего
патча; `delta` — 0 (предупреждения — в выводе); все команды — 2 при ошибке (`error: ...`).

`merge_conflicts.json`:

```json
{ "schema": 1, "game": "v1.4.0",
  "pairs": [ { "a": "x@1.2.0", "b": "y@0.3.1", "file": "scripts\\sim_squad.script",
               "atoms": ["sim_squad.get_spawn_section_name"], "patch": "compat_x_y@1.0.0", "patch_resolves": true } ] }
```

Необязательные поля пары: `fallback` — текст ошибки, если слитый файл не прошёл проверку и движок отдаст файл верхнего
аддона целиком (`atoms` тогда может быть пустым); `patch_stale` — id аддонов пары, чьи файлы не совпали с отпечатками
`<патч>\merge\targets.ltx` (§6.1 плана): движок применяет такой фрагмент, но его конфликты считает нерешёнными, поэтому
`patch_resolves` = `false`. Скрипты проверяются компиляцией LuaJIT, как в движке (`gw_merge --check-lua`): библиотека
ищется рядом с `gw_merge`, затем в `xray-16\bin\x64\Release`, или задаётся `--check-lua <LuaJIT.dll>`. Без неё
`pairs` предупреждает: `fallback` из-за некомпилирующегося Lua не виден.

`merge_stats.json` — атомы по убыванию числа аддонов: `{"file", "atom", "addons", "conflict_pairs", "patched"}`.
Это список кандидатов на событие, хук или реестр в базе (13 §4.7). Ещё в нём пропущенные из-за лимита пары
(`max_pairs_per_file`, `skipped_pairs`, `skipped`) — см. «Кэш и лимит пар» ниже.

Дельту аддона `pairs` выбирает как движок: только `<аддон>\.gw_merge\delta.json`; битый файл (не JSON, повтор ключа, не дельта формата 1) — предупреждение
и аддон без дельты. С `--catalog` — только дельта каталога `files/<id>/<ver>.json`, `.gw_merge\` пакета не читается
никогда (15 §2.3, ревью B6): лаунчер ставит дельту каталога, а если её нет — удаляет дельту пакета. Аддон без дельты
(локальный), а также файл, для которого дельта устарела (другой `algo` или файл правили после публикации —
`addon_sha256`, `stale_delta`), участвует атомами `gw_merge atoms` против последней базы — как его сольёт движок без
дельты (S8). Изменённый контейнер (секция, узел xml) при этом не считается отдельным атомом — только его изменённые
дети, как в дельте. Промежутки дельты `@gap <метка>` сравниваются по `<метка>` (так их называют `atoms` и конфликты
слияния), а файл дельты `kind: lines` (`@lines`) пересекается с любым атомом другого аддона.

Пары отбираются по общему атому (13 §4.7). Исключение — скрипты (`.script`): пара, где оба аддона меняют один скрипт,
сливается и компилируется, даже если их атомы разные: непересекающиеся правки вместе могут не компилироваться
(например, у каждого по 110 `local` в одной функции — больше 200), и движок тогда отдаёт файл верхнего аддона
целиком. Такая пара попадает в `merge_conflicts.json` обычной записью с `fallback` (текст ошибки компиляции) и
обычно пустым `atoms`, учитывается в коде выхода 1 и проверяется патчем совместимости, как остальные. Без LuaJIT
такие пары не сливаются (проверять нечем) — `pairs` предупреждает. Пример — тестовые аддоны `test_merge_b` и
`test_merge_bad` (`scripts\bind_faction.script`, разные функции): запись с
`fallback: scripts\bind_faction.script:52: main function has more than 200 local variables`. Для `.ltx` и `.xml`
пары по-прежнему только с общим атомом.

#### Кэш и лимит пар

Число пар на популярный файл растёт как n²/2, а одно слияние `gw_merge` такого файла — около 25 мс. Поэтому:

- `--cache <папка>` — результаты пар (конфликтующие атомы, `fallback`, `patch_resolves`) по ключу sha256 от: текста
  базы, файла и файла дельты каждой стороны (с id аддона), патча пары (id, `patches`, sha256 фрагмента, `patch_stale`),
  `algo` и sha256 бинарника `gw_merge`, флага `--check-lua`. Повторный прогон сливает только пары, у которых что-то
  из этого изменилось; кэшируются и пары без конфликта. Запись — `<папка>\<2 hex>\<ключ>.json` (через временный файл
  и переименование); битая запись — предупреждение и слияние заново. По умолчанию кэша нет: `--out-dir` в CI — это
  репозиторий индекса, кэш туда класть нельзя (в CI — отдельная папка под `actions/cache`).
- `--max-pairs-per-file N` (по умолчанию 200, `0` — без лимита) — не больше N слияний `gw_merge` на файл за прогон.
  Пары, взятые из кэша, в лимит не входят: с `--cache` каждый следующий прогон проверяет следующие N пар, пока не
  проверит все. Сверх лимита первыми идут пары с аддонами из `--changed <id>[,<id>...]` (новые и обновлённые с прошлого
  прогона: id, `id@версия` или имя папки; сначала пары, где изменились оба), затем — порядок аддонов в командной
  строке. Остальные пропускаются: их конфликтов нет в `merge_conflicts.json`, код выхода они не меняют.

Пропуски видны в `merge_stats.json` и в stderr (`warning: pairs: N pair(s) of M file(s) are NOT checked ...` и строка
на каждый файл); там же — сколько пар слито и сколько взято из кэша:

```json
{ "schema": 1, "game": "v1.4.0", "atoms": [ ... ],
  "max_pairs_per_file": 200, "skipped_pairs": 37,
  "skipped": [ { "file": "scripts\\sim_squad.script", "pairs": 437, "checked": 400, "skipped": 37 } ] }
```

`pairs` — все пары-кандидаты файла, `checked` — взятые из кэша и слитые в этом прогоне.
